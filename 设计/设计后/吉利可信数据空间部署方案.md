### 3.2 什么是Pod？

**Pod** 是 Kubernetes 的最小部署单元，可以理解为一个"容器盒子"，里面运行着我们的 API 服务。

```
┌─────────────────────────────────────────────────────────────┐
│                    Kubernetes 集群                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐                   │
│   │  Pod 1  │  │  Pod 2  │  │  Pod 3  │   ...              │
│   │ ┌─────┐ │  │ ┌─────┐ │  │ ┌─────┐ │                   │
│   │ │ API │ │  │ │ API │ │  │ │ API │ │                   │
│   │ │服务 │ │  │ │服务 │ │  │ │服务 │ │                   │
│   │ └─────┘ │  │ └─────┘ │  │ └─────┘ │                   │
│   └─────────┘  └─────────┘  └─────────┘                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 为什么需要多个Pod？

| 优点 | 说明 |
|------|------|
| **处理并发** | 1个Pod只能处理150并发，20个才能处理3000并发 |
| **高可用** | 1个Pod挂了，还有19个继续服务，用户无感知 |
| **滚动更新** | 可以一个一个更新，不中断服务 |
| **资源隔离** | 避免单点资源瓶颈 |

**简单类比：**

```
❌ 单个厨师 (1个Pod)
   - 只能同时做10道菜
   - 厨师病了/休息就没人做菜

✓ 20个厨师 (20个Pod)
   - 同时能做200道菜
   - 1个厨师请假还有19个
   - 可以轮流休息
```

### 3.4 3000并发容量计算

```
┌────────────────────────────────────────────────────────────────────────────────┐
│                           3000并发容量计算                                      │
├────────────────────────────────────────────────────────────────────────────────┤
│                                                                               │
│  用户请求 ──▶ Nginx负载均衡 ──▶ 20个API Pod                                    │
│                              │                                                 │
│                              ├──▶ TDS API (每Pod 150并发)                        │
│                              │    × 20 = 3000并发                               │
│                              │                                                  │
│                              └──▶ 20 Pod × 50连接/Pod = 1000 MySQL连接           │
│                                                                               │
│  结论: 3000并发 完全满足，预留20%余量                                            │
│                                                                               │
└────────────────────────────────────────────────────────────────────────────────┘
```

**Pod数量计算公式：**

```
3000并发 ÷ 150并发/Pod = 20个Pod

预留20%余量应对突发:
3000 × 1.2 = 3600并发 ÷ 150 = 24个Pod

HPA自动扩缩配置:
- 最小副本: 3个 (基础保障)
- 最大副本: 25个 (预留约20%)
- 扩容条件: CPU>70% 或 内存>80%
```

## 四、高可用设计

### 4.1 什么是高可用？

**高可用 (High Availability)** 是指系统在大部分时间都能正常运行，即使发生故障也能快速恢复。

```
┌─────────────────────────────────────────────────────────────────┐
│                    高可用 vs 不可用                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ❌ 不可用系统:                                                    │
│     用户请求 ──▶ 服务器挂了 ──▶ ❌ 服务崩溃，用户无法使用           │
│                                                                  │
│  ✓ 高可用系统:                                                     │
│     用户请求 ──▶ 服务器A挂了 ──▶ 自动切换到服务器B ──▶ ✅ 继续服务   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 五、分布式架构

### 5.1 为什么需要分布式架构？

**场景说明：** 连接器可能部署在吉利的客户机房，数据源在客户本地（如ERP、MES系统），但服务平台在吉利数据中心。

```

│  吉利数据中心                                                    客户机房     │
│  ┌────────────────┐                              ┌────────────────┐       │
│  │  服务平台(TDS)  │◀───── VPN/专线 ────────────▶│  连接器(Datar) │       │
│  │  交付平台(DOS)  │       安全隧道              │  数据源(ERP等)  │       │

└─────────────────────────────────────────────────────────────────────────────┘
```

**设计优点：**

| 优点 | 说明 |
|------|------|
| **数据安全** | 数据源在客户机房，无需将原始数据传输到吉利数据中心 |
| **合规要求** | 满足数据不出机房的安全合规要求 |
| **网络简化** | 客户机房只需开放连接器端口，减少防火墙配置 |

## 九、性能指标

### 9.1 指标说明

| 指标 | 说明 |
|------|------|
| **并发用户** | 同时操作系统的用户数量 |
| **API QPS** | 每秒处理的请求数量 |
| **P99延迟** | 99%的请求在多少毫秒内完成 |
| **数据库TPS** | 数据库每秒处理的事务数 |
| **可用率** | 系统正常运行时间占比 |

**为什么关注P99而不是平均延迟？**

```
请求延迟分布:
  100ms ████████████████████████████ 95%
  200ms ████ 3%
  500ms ██ 1%
 1000ms █ 0.5%

平均延迟: 115ms (看起来不错)
P99延迟: 200ms (真实用户体验)

问题: 5%的用户遇到超过200ms的延迟，平均值看不到这个问题
```

### 9.2 高并发指标

| 指标 | 设计值 | 目标值 | 说明 |
|------|--------|--------|------|
| **并发用户** | 3000 | 3500+ | 预留20%+余量 |
| **API QPS** | 3000 | 4000 | 每秒请求数 |
| **P99延迟** | < 150ms | < 200ms | 99分位响应 |
| **数据库TPS** | 2000 | 2500 | 数据库处理能力 |
| **Redis QPS** | 10万 | 15万 | 缓存处理能力 |

### 9.2 高可用指标

| 指标 | 设计值 | 说明 |
|------|--------|------|
| **可用率** | 99.9% | 年度停机 ≤ 8.76小时 |
| **MTTR** | < 30分钟 | 平均恢复时间 |
| **RTO** | < 30秒 | 恢复时间目标 |
| **RPO** | < 1秒 | 恢复点目标 |

**RTO/RPO 解释：**

```
┌─────────────────────────────────────────────────────────────────┐
│                    RTO 和 RPO 解释                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  RTO (Recovery Time Objective) - 恢复时间目标                    │
│  例: 系统挂了，多久能恢复？                                       │
│  我们的目标: < 30秒                                              │
│                                                                  │
│  RPO (Recovery Point Objective) - 恢复点目标                      │
│  例: 系统恢复后，最多能丢失多少数据？                              │
│  我们的目标: < 1秒 (最多丢失1秒的数据)                          │
│                                                                  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  故障点 ──────|─────────────────── 恢复完成              │  │
│  │              │                                              │  │
│  │              ▼                                              │  │
│  │          RTO < 30秒                                         │  │
│  │                                                           │  │
│  │  能丢失的数据                                                │  │
│  │  ◄───────── RPO < 1秒 ─────────►                         │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

| 指标 | 设计值 | 说明 |
|------|--------|------|
| **可用率** | 99.9% | 年度停机 ≤ 8.76小时 |
| **MTTR** | < 30分钟 | 平均恢复时间 |
| **RTO** | < 30秒 | 恢复时间目标 |

### 11.3 备份策略

| **MySQL** | 每日全量 | 30天 | 增量binlog |
| **Redis** | 每小时RDB | 7天 | AOF重放 |
| **Kafka** | 话题配置3副本 | 7天 | 副本重放 |
| **配置** | 每次变更 | 90天 | 配置中心 |
